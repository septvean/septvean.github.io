FAQ

sqlalchemy 中，sessionmaker 如何不使用 with，直接调用 

db_engine = create_engine(url=db_url, future=True)
db_session = sessionmaker(bind=db_engine)
with db_session() as session:

sqlalchemy 中，sessionmaker 如何不使用 with，直接调用?

在 SQLAlchemy 中，如果不使用 with 上下文管理器，你需要手动管理 Session 的开启与关闭（特别是通过 try...finally 块确保连接最终被释放）。

以下是直接调用的标准写法：

1. 推荐写法：使用 try…finally 确保关闭

如果不使用 with，必须在操作完成后手动调用 session.close()，否则会导致数据库连接泄露。

# 1. 实例化得到 session 对象
session = db_session()

try:
    # 2. 执行你的数据库操作
    result = session.execute(stmt)
    # 如果有修改操作，需要手动 commit
    session.commit()
except Exception as e:
    # 发生异常时回滚
    session.rollback()
    raise e
finally:
    # 3. 无论成功与否，必须关闭 session 以释放连接
    session.close()

2. 为什么不推荐直接拿来就用？

如果你省去 try...finally，直接这样写：

session = db_session()
user = session.query(User).filter_by(id=1).first()
# 忘记调用 session.close() —— 危险！
  • 后果：这会导致该连接一直被占用，无法放回 SQLAlchemy 的连接池（Connection Pool）中。当高并发或者循环执行这段代码时，数据库连接很快就会被耗尽，报 TimeoutError: QueuePool limit of size X overflow Y reached 错误。

💡 更好的替代方案：Scoped Session（线程安全）

如果你是不想在每个函数里都写 with 或 try...finally，通常在 Web 框架（如 Flask）或多线程应用中，会使用 scoped_session 来全局管理：

from sqlalchemy.orm import scoped_session, sessionmaker

db_engine = create_engine(url=db_url, future=True)
session_factory = sessionmaker(bind=db_engine)
# 创建一个作用域 session
Session = scoped_session(session_factory)

# 在需要的地方直接使用，它在当前线程/请求中是唯一的
session = Session()
result = session.execute(stmt)

# 在请求结束或线程结束时，统一移除（会自动关闭连接）
Session.remove()

如果使用 with，如何写成公用的函数

将 with 语法封装成公用函数，在 Python 中最优雅、最标准的方法是使用 上下文管理器（Context Manager）。

你可以利用标准库的 contextlib.contextmanager 装饰器，将数据库的“打开、提交、异常回滚、关闭”这一套标准流程封装起来。

📌 最佳实践：使用装饰器封装公用函数

你可以创建一个全局的 get_db() 函数：

from contextlib import contextmanager
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

# 初始化 Engine 和 Session 工厂
db_engine = create_engine(url=db_url, future=True)
db_session = sessionmaker(bind=db_engine)

# ================= 公用上下文管理器 =================
@contextmanager
def get_db():
    """公用数据库连接上下文管理器"""
    session = db_session()
    try:
        yield session  # 将 session 传递给 with 语句
        session.commit()  # 如果没有报错，自动提交（可选，不需要自动提交可以删掉这行）
    except Exception as e:
        session.rollback()  # 发生异常自动回滚
        raise e
    finally:
        session.close()  # 无论如何都会关闭连接释放池

🚀 如何在其他地方使用？

封装好后，在你的业务代码中只需要一行 with 即可，完全不用再担心忘记关闭连接或忘记处理回滚：

# 1. 执行查询操作
with get_db() as session:
    users = session.execute(stmt).all()
    # 离开 with 块时，session 会自动关闭

# 2. 执行写入/修改操作（由于封装了 commit，这里连 commit 都不用写了）
with get_db() as session:
    new_user = User(name="张三")
    session.add(new_user)
    # 离开 with 块时，如果没有报错，会自动 commit 并 close

💡 为什么推荐这种写法？

  1. 安全彻底：即使 yield 后面的业务代码（with 内部）发生了报错抛出异常，finally 块也一定会执行，确保连接绝不泄露。
  2. 逻辑内聚：把 commit 和 rollback 统一托管。如果你不希望它自动 commit（更习惯在业务里手动写 session.commit()），只需把公用函数里的 session.commit() 那一行删掉即可。

如果你使用的是 FastAPI 框架，它的依赖注入系统（Dependency Injection）正好能完美原生支持这种 yield 结构的函数。

sessionmaker 的类型是什么

在 SQLAlchemy 中，sessionmaker 的类型根据你是在谈论它本身，还是它实例化后的工厂对象，会有所不同。

在声明类型提示（Type Hints）时，最核心的答案是：sessionmaker 本身是一个类，而它调用后生成的对象是一个连接工厂，类型为 sessionmaker（在运行时实际是一个包装了 Session 的类）。

以下是完整的类型映射和在代码中写类型提示（Type Hints）的标准方法：

1. 业务中最常用的类型：Session

当你调用 db_session()（即你的工厂对象）或者通过 with get_db() as session: 获取到的那个 session 变量，它的类型是 sqlalchemy.orm.Session。

这是你最常需要写类型提示的地方：

from sqlalchemy.orm import Session

# 明确指定 session 的类型为 Session
def get_user_by_id(session: Session, user_id: int):
    return session.query(User).filter_by(id=user_id).first()

2. 工厂对象本身的类型：sessionmaker

在你的代码中，db_session = sessionmaker(bind=db_engine) 这一步得到的 db_session，它的类型就是 sqlalchemy.orm.sessionmaker。

如果你要将这个“工厂”作为参数传递给其他函数，应该这样写类型提示：

from sqlalchemy.orm import sessionmaker

# db_session_factory 的类型是 sessionmaker
def init_app(db_session_factory: sessionmaker):
    # 它是一个可以被调用的工厂，调用后返回 Session 对象
    session = db_session_factory()

3. 在 Python 10 及以上/最新 SQLAlchemy 中的完整类型规范

如果你使用的是 SQLAlchemy 2.0（或开启了 future=True 的 1.4），配合 Python 的 typing 模块，它的底层完整泛型定义其实是 sessionmaker[Session]。

标准的全局声明和类型定义看起来像这样：

from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker, Session

db_engine = create_engine(url=db_url, future=True)

# 显式指定类型（特别是使用现代 IDE 如 PyCharm, VS Code 时，这样能获得完美的自动补全）
db_session: sessionmaker[Session] = sessionmaker(bind=db_engine)

如何查看 CursorResult, Result, ScalarResult 的数据

在 SQLAlchemy 1.4/2.0 中，执行 session.execute() 后会返回一个 Result 对象。为了高效处理内存，这些对象都属于迭代器（Iterator）/生成器风格，这意味着它们只能被读取（消耗）一次。

下面是查看这三种对象数据的标准方法和它们之间的区别：

1. Result (基础结果集)

Result 是最通用的结果对象。它返回的每一行默认都是一个 Row 对象（类似于命名元组 namedtuple）。

  • 获取全部数据（列表）：.all()
  • 获取第一行：.first()（如果没数据返回 None）
  • 获取唯一的一行：.one()（如果没数据或有多条数据会报错）
  • 转为字典列表：.mappings().all() （推荐，最直观）
result = session.execute(stmt)

# 方式 A：转为字典列表查看（最适合打印和查看结构）
print(result.mappings().all()) 
# 输出: [{'id': 1, 'name': '张三'}, {'id': 2, 'name': '李四'}]

# 方式 B：直接循环遍历行
# for row in result:
#     print(row.id, row.name)  # 可以通过属性访问

2. ScalarResult (单列/标量结果集)

当你使用 .scalars() 后，Result 会变成 ScalarResult。它会自动把每一行的第一个字段抠出来。通常在查询整型列表或ORM 实例对象列表时使用。

  • 获取全部数据（列表）：.all()
  • 获取第一个元素：.first()
# 查询所有的用户对象
scalar_result = session.scalars(select(User))

# 查看数据：
user_list = scalar_result.all()
print(user_list)  # 输出: [<User id=1>, <User id=2>]

3. CursorResult (原生 SQL 执行结果)

当你执行的是纯原生 SQL（如 session.execute(text("SELECT ..."))）或者 INSERT/UPDATE/DELETE 语句时，返回的是 CursorResult。它继承自 Result，但带有底层数据库驱动（DBAPI）的特性。

  • 查看受影响的行数（针对更新/删除）：.rowcount
  • 查看自增 ID（针对插入）：.inserted_primary_key
  • 查看数据：方法与 Result 完全一致（如 .mappings().all()）
from sqlalchemy import text

cursor_result = session.execute(text("SELECT id, name FROM users"))

# 查看原生 SQL 数据：
print(cursor_result.mappings().all())

💡 核心总结与避坑指南

  1. 不要重复读取：如果你执行了 print(result.all())，由于结果集已经被“消耗”完了，紧接着再写 result.all() 就会返回空列表 []。

  2. 快速查看快捷键：

    • 想看字典格式：用 result.mappings().all()
    • 想看纯对象/纯值列表：用 result.scalars().all()

如何查看 CREATE TABLE 返回的结果

在 SQLAlchemy 中执行 CREATE TABLE 语句时，返回的对象类型通常是 CursorResult。

但需要特别注意的是：CREATE TABLE 属于数据定义语言（DDL），在关系型数据库中，它本身是不返回任何数据行（Row）的。 因此，你无法像 SELECT 语句那样通过 .all() 或 .mappings() 去读取数据。

如果你想确认建表操作的结果，通常有以下几种方式：

1. 检查受影响状态（最直接）

虽然没有数据返回，但你可以通过 CursorResult 对象的底层属性来确认执行状态。

from sqlalchemy import text

# 执行建表语句
cursor_result = session.execute(text("""
    CREATE TABLE IF NOT EXISTS test_table (
        id INT PRIMARY KEY,
        name VARCHAR(50)
    )
"""))

# 1. 查看受影响行数（建表语句通常返回 0 或 -1，取决于数据库驱动，但只要不报错就代表成功）
print(cursor_result.rowcount)

# 2. 检查是否有返回的数据（建表语句这里必然是 False）
print(cursor_result.returns_rows)  # 输出: False
  • 结论：在执行 DDL 时，只要代码没有抛出异常（Exception），就说明表已经创建成功了。

2. 通过「检查器（Inspector）」反查表是否真的存在（推荐）

如果你想在执行完 CREATE TABLE 后，100% 确认表已经在数据库中生成，并查看它的结构，应该使用 SQLAlchemy 的 inspect 工具，而不是去读 execute() 的返回值。

from sqlalchemy import inspect

# 获取数据库检查器
inspector = inspect(db_engine)

# 1. 查看数据库中所有的表名，确认你的表是否在里面
all_tables = inspector.get_table_names()
print("当前数据库中的表:", all_tables)

if "test_table" in all_tables:
    print("表 test_table 创建成功！")
    
    # 2. 进一步查看这个表的字段信息
    columns = inspector.get_columns("test_table")
    for col in columns:
        print(f"字段名: {col['name']}, 类型: {col['type']}, 是否允许为空: {col['nullable']}")

3. 如果是用 ORM 的 Base.metadata.create_all()

如果你不是用原生 SQL，而是用 SQLAlchemy 标准的 ORM 模型建表：

# 这行代码同样没有返回值（返回 None）
Base.metadata.create_all(db_engine)

如果你想查看它到底执行了什么 SQL，可以在创建引擎时开启回显 echo=True，这样在控制台（Terminal）里就能直接看到完整的 CREATE TABLE ... 打印日志：

db_engine = create_engine(url=db_url, future=True, echo=True) # 开启 echo

返回的结果类型为 Result | CursorResult | ScalarResult | None，新声明的变量 如何只使用 CursorResult | None

在 Python 中，当一个函数的返回值可能是多种结果的联合类型（Union Type），而你明确知道在当前的特定场景下（比如执行了 CREATE TABLE 或 INSERT），它只会是 CursorResult 或 None 时，你可以通过以下几种标准方式来收窄类型（Type Narrowing）并安全地声明新变量。

这样做不仅能满足 mypy 等静态类型检查，还能让 IDE（如 PyCharm/VS Code）完美提供代码自动补全。

1. 使用 cast 强制重新声明（最标准、最直接）

如果你非常确定返回结果的类型，可以使用 Python typing 模块中的 cast。它只在编译期/静态检查时起作用，不会带来任何运行时的性能损耗。

from typing import cast, Optional
from sqlalchemy.engine import CursorResult

# 1. 假设这是你的公用执行函数，返回联合类型
raw_result = session.execute(stmt) 

# 2. 将新变量显式声明并强制转换（Python 3.10+ 语法）
result: CursorResult | None = cast(CursorResult, raw_result)

# 如果是 Python 3.9 及以下版本，使用 Optional：
# result: Optional[CursorResult] = cast(CursorResult, raw_result)

# 现在 IDE 会完全理解 result 的类型，输入 result. 后会自动提示 .rowcount / .returns_rows
if result:
    print(result.rowcount)

2. 使用 isinstance 运行时类型检查（最安全）

如果你希望代码在运行时也具备健壮性，能够自动识别并收窄类型，可以使用 isinstance。静态类型检查工具（如 mypy、pyright）看到 isinstance 后，会自动将大范围类型收窄。

from sqlalchemy.engine import CursorResult

raw_result = session.execute(stmt)

# 使用 isinstance 检查，类型检查器会自动将 result 锁定为 CursorResult | None
result = raw_result if isinstance(raw_result, CursorResult) else None

# 此时 result 的类型就已经完美缩减为 CursorResult | None
if result:
    print(result.rowcount)

3. 利用类型注解与 assert 断言

如果你不想引入 cast，也可以直接通过类型注解声明新变量，并配合 assert 来让类型检查器放心。

from sqlalchemy.engine import CursorResult

raw_result = session.execute(stmt)

# 1. 直接为新变量打上你想要的类型标签
result: CursorResult | None = raw_result  # 如果开启了严格检查，这里可能会报警告

# 2. 用断言消除警告，并告诉 IDE：它绝对不是 Result 或 ScalarResult
if result is not None:
    assert isinstance(result, CursorResult)
    print(result.rowcount)  # 安全使用

💡 为什么需要引入 CursorResult 模块？

需要特别注意：Result、ScalarResult 可以在 sqlalchemy 或 sqlalchemy.orm 中直接导入。但 CursorResult 的真实具体类位于 sqlalchemy.engine 模块中。

所以在文件的顶部，记得确保这样导入：

from sqlalchemy.engine import CursorResult

使用 ORM Insert 插入数据

在 SQLAlchemy 2.0 中，使用 ORM 进行 INSERT 操作主要有两种流派：传统的 ORM 实例对象流派（最直观，支持外键级联）和 2.0 推荐的 insert() 表达式流派（性能极高，支持批量插入）。

下面是这两种方法的标准写法以及如何获取插入后的结果（如自增 ID）：

方法一：传统 ORM 实例流派（推荐用于单条、有业务逻辑的场景）

这是最经典的写法。你直接实例化定义好的模型类，然后将其添加到 session 中。

from sqlalchemy import create_engine, Column, Integer, String
from sqlalchemy.orm import declarative_base, sessionmaker

Base = declarative_base()

# 定义模型
class User(Base):
    __tablename__ = 'users'
    id = Column(Integer, primary_key=True, autoincrement=True)
    name = Column(String(50))

# 1. 创建实例对象
new_user = User(name="张三")

with get_db() as session:  # 使用前面封装好的公用函数
    # 2. 将对象添加到会话中
    session.add(new_user)
    
    # 3. 此时数据还在内存缓存中，调用 flush() 或 commit() 会将其写入数据库并生成自增 ID
    session.flush() 
    
    # 4. 查看插入后的自增 ID
    print(f"新插入用户的 ID 是: {new_user.id}") 
    
    # 如果公共函数里没有写 commit，记得在这里手动调用：session.commit()

方法二：SQLAlchemy 2.0 insert() 表达式流派（推荐用于批量、高性能场景）

如果你使用的是 SQLAlchemy 2.0 的新语法，或者希望批量插入多条数据，推荐使用 insert(Model).values(…)。这种写法在执行后会返回一个 CursorResult。

1. 插入单条并获取自增 ID 

from sqlalchemy import insert

with get_db() as session:
    # 构建 insert 语句
    stmt = insert(User).values(name="李四")
    
    # 执行语句，返回 CursorResult
    result = session.execute(stmt)
    
    # 查看受影响行数
    print(f"受影响行数: {result.rowcount}") # 输出: 1
    
    # 查看最新生成的自增主键（返回一个元组）
    print(f"生成的自增 ID 元组: {result.inserted_primary_key}") # 输出类似: (2,)
    print(f"生成的自增 ID 整数: {result.inserted_primary_key[0]}") # 输出: 2

2. 批量插入多条数据（极其高效）

如果你需要一次性向数据库插入成百上千条数据，直接传递一个字典列表给 values()，SQLAlchemy 会自动将其优化为单条批量 SQL 执行（底层使用驱动的 executemany）：

from sqlalchemy import insert

# 准备批量数据列表
data_list = [
    {"name": "王五"},
    {"name": "赵六"},
    {"name": "孙七"}
]

with get_db() as session:
    # 2.0 语法中，直接将列表传给 values()
    stmt = insert(User).values(data_list)
    
    result = session.execute(stmt)
    print(f"批量成功插入了 {result.rowcount} 条数据")

3. 批量插入并返回所有的对象或 ID (RETURNING 语法)

如果你的数据库支持（如 PostgreSQL、SQLite 3.35+、MariaDB 10.5+），你可以使用 .returning() 拿到插入后的完整数据。此时它会返回一个 Result 对象：

from sqlalchemy import insert

stmt = insert(User).values([{"name": "A"}, {"name": "B"}]).returning(User)

with get_db() as session:
    # 此时返回的是 Result，可以用 scalars() 转为模型对象
    inserted_users = session.scalars(stmt).all()
    for user in inserted_users:
        print(f"成功插入: ID={user.id}, Name={user.name}")

💡 核心避坑提示

  • 如果使用 方法一（session.add()），在 commit() 或 flush() 之前，主键 user.id 是 None。必须触发数据库写入后才能获取到 ID。
  • 如果使用 方法二（insert() 表达式），在不支持 RETURNING 语法的数据库（如老版本 MySQL）中执行批量插入时，result.inserted_primary_key 可能无法返回所有插入的 ID，通常只能拿到最后一条或报错。如果批量插入且必须拿回所有 ID，推荐使用 RETURNING 语法或回归方法一的 session.add_all([user1, user2])。

inspector.get_table_names() 如何多次调用

在 SQLAlchemy 中，inspector.get_table_names() 能否多次调用，取决于你是如何获取 inspector 对象的。

核心结论：如果数据库在运行期间有表结构变动（比如新创建了表），直接重复调用同一个 inspector 实例是拿不到最新数据的。 因为 Inspector 在初始化时通常会缓存（Cache）当前的数据库元数据。

为了实现多次安全、准确地调用，你可以采用以下两种方案：

方案一：每次调用前，重新生成 inspector（推荐，最安全）

如果你在代码的上下文中执行了 CREATE TABLE 或 DROP TABLE，并希望紧接着查看最新的表名单，最稳妥的方法是重新调用 inspect(engine)。因为重新实例化会强制向数据库发起最新的查询，绕过缓存。

from sqlalchemy import inspect

# 第一次查看
inspector1 = inspect(db_engine)
print("修改前的表:", inspector1.get_table_names())

# ... 这里执行了某个建表操作 ...
# session.execute(text("CREATE TABLE new_table (...)"))

# 第二次查看：必须重新获取 inspect 对象，确保拿到最新状态
inspector2 = inspect(db_engine)
print("修改后的最新表:", inspector2.get_table_names())

方案二：如果你使用的是 Connection（连接级别），可以使用 with 多次调用

如果你将 inspect() 绑定在 engine 上，每次直接重复调用同一个实例可能读到缓存。但如果你是在一个持有的连接（Connection）上，并且希望在同一个连接会话中多次查看，可以通过重新建立连接来刷新，或者像下面这样写成一个工具函数：

def check_tables_now(engine) -> list[str]:
    """每次调用都实时获取最新表名的工具函数"""
    # 每次获取最新的连接并查看
    with engine.connect() as connection:
        return inspect(connection).get_table_names()

# 随时随地多次调用该函数，保证每次都是最新数据：
tables_v1 = check_tables_now(db_engine)
# ... 执行建表 ...
tables_v2 = check_tables_now(db_engine)

💡 为什么多次调用可能失效？（避坑指南）

如果你在一个长生命周期的类或脚本中写成了下面这样：

class DBManager:
    def __init__(self, engine):
        self.inspector = inspect(engine)  # 错误做法：在初始化时固定了 inspector

    def show_tables(self):
        # 即使你调用这个方法 100 次，在整个程序运行期间它返回的永远是初始状态的那几个表
        return self.inspector.get_table_names()

正确的面向对象写法应该是：

class DBManager:
    def __init__(self, engine):
        self.engine = engine  # 只保存 engine

    def show_tables(self) -> list[str]:
        # 每次调用时实时生成，确保多次调用结果准确
        return inspect(self.engine).get_table_names()

session.execute 执行 orm insert，为什么 result.rowcount 为 -1

在 SQLAlchemy 中，使用 session.execute(insert(Model).values(...)) 执行 ORM Insert 时，result.rowcount 返回 -1（或者在某些驱动中返回 None）通常是因为：你使用的是不完整支持标准 rowcount 反馈的数据库驱动（如 sqlite 或某些旧版本的 mysql 驱动），或者触发了 SQLAlchemy 的批处理优化。

在 Python DBAPI（数据库驱动规范）中，对于非 UPDATE 或 DELETE 语句，驱动程序并不被强制要求返回一个有意义的 rowcount。当驱动无法确切提供或计算该值时，它就会默认返回 -1。

以下是导致 -1 的三大核心原因以及解决方法：

1. 驱动或数据库本身的限制（最常见原因）

SQLite / MySQL: 在执行某些复杂的批量插入或带特定条件的写入时，底层驱动（如 sqlite3、pymysql）可能无法向 SQLAlchemy 报告受影响的行数，因此安全地返回 -1。

验证方法：如果你改用 UPDATE 或 DELETE 语句，通常能正常拿到大于 0 的 rowcount。但对于 INSERT，rowcount 在跨数据库移植时是非常不可靠的。

2. 触发了高效率的 executemany（批量插入）

如果你向 values() 传递了一个字典列表进行批量插入：

stmt = insert(User).values([{"name": "A"}, {"name": "B"}])
result = session.execute(stmt)

SQLAlchemy 底层会将其优化为驱动级别的 executemany 执行。很多数据库驱动在执行 executemany 时，故意不计算总行数以提升性能，或者其规范规定此时 rowcount 应当为 -1。

3. 使用了 RETURNING 语法

如果你在 insert 后面加上了 .returning(User.id)：

stmt = insert(User).values(name="A").returning(User.id)
result = session.execute(stmt)

一旦语句带有 RETURNING（通常在 PostgreSQL 或最新版 SQLite 中），该 SQL 的行为在底层会从“执行写入命令”转变为“执行类似 SELECT 的查询命令”。由于它变成了一个数据流结果集，很多驱动就不再提供 rowcount，而是让你通过迭代结果来感知拿到了多少条数据。

🛠️ 解决方案：如何正确获取插入结果？

如果你需要确认数据是否插入成功，或者想知道插入了多少条，不要依赖 rowcount。请使用以下替代方案：

方案 A：如果只需要知道插入了多少条数据

由于你是自己在代码里构建的列表，最直接也最高效的方法是直接计算你传入的列表长度：

data_to_insert = [{"name": "A"}, {"name": "B"}]

stmt = insert(User).values(data_to_insert)
session.execute(stmt)

# 只要没报错，插入的行数就是你数据的长度
inserted_count = len(data_to_insert) 
print(f"成功插入了 {inserted_count} 条数据")

方案 B：如果需要确认单条插入的自增 ID

如果是单条插入，利用 inserted_primary_key 属性来验证（如果成功，它会返回新数据的 ID，这就间接证明了插入成功）：

stmt = insert(User).values(name="张三")
result = session.execute(stmt)

if result.inserted_primary_key:
    print(f"插入成功，自增 ID 为: {result.inserted_primary_key[0]}")

方案 C：使用 RETURNING 并通过 len() 计算（推荐高级数据库使用）

如果你使用的是 PostgreSQL 或支持的数据库，可以通过获取返回结果的数量来精确计算行数：

stmt = insert(User).values(data_list).returning(User.id)
result = session.execute(stmt)

# 将结果转换为列表，它的长度就是真实插入的行数
inserted_ids = result.scalars().all()
print(f"真实成功插入了 {len(inserted_ids)} 行")

PostgreSQL

在 PostgreSQL 中使用 SQLAlchemy 执行 session.execute(insert(Model).values(...)) 时，result.rowcount 返回 -1，绝大多数情况下是因为：SQLAlchemy 2.0 在配合 PostgreSQL 驱动（如 psycopg2 或 psycopg）执行批量插入时，默认启用了极其高效的「快速执行（Fast Execution）」机制，导致驱动层无法或不提供 rowcount。

以下是触发 -1 的底层深层原因以及在 PostgreSQL 下的最佳解决办法：

🔍 为什么在 PostgreSQL 中会变成 -1？

  1. 底层触发了 executemany 优化

    当你传入一个列表（批量插入）时，SQLAlchemy 2.0 默认会合并这些插入。由于 Python 的 DBAPI 规范中，很多驱动在执行完 executemany 之后，rowcount 字段本身就是未定义的（Undefined），驱动为了安全和性能，直接返回 -1。

  2. SQLAlchemy 自动附加了隐式的 RETURNING

    SQLAlchemy 2.0 为了确保能拿回新插入行的自增主键或默认值，通常会在后台秘密地将你的 INSERT 语句改写为 INSERT … RETURNING …。

    • 关键逻辑：一旦 SQL 语句中带有 RETURNING，PostgreSQL 驱动会认为这是一个**「返回数据流的结果集」（类似 SELECT）**，而不是一个单纯的受影响行命令。很多版本的 psycopg 驱动在面对带有返回结果的数据流时，其 rowcount 属性就会失效，返回 -1。

🛠️ PostgreSQL 环境下的 3 种完美替代方案

在 PostgreSQL 中，如果你想明确地知道插入了多少条数据，或者验证是否插入成功，请放弃使用 rowcount，改用下面更契合 Postgres 特性的写法：

方案一：显式使用 .returning() 并统计数量（最推荐，最 Postgres 化）

由于 PostgreSQL 完美支持 RETURNING，你可以直接让它把每一行的 ID 或主键返回来。你只需要通过 len() 计算结果集的长度，就能100% 精确知道插入了多少行。

from sqlalchemy import insert

data_list = [{"name": "用户A"}, {"name": "用户B"}, {"name": "用户C"}]

# 显式要求返回 id 列
stmt = insert(User).values(data_list).returning(User.id)

with get_db() as session:
    result = session.execute(stmt)
    # 获取所有返回的 ID 列表
    inserted_ids = result.scalars().all()
    
    # 结果的长度就是最真实的成功插入行数
    print(f"PostgreSQL 真实插入成功行数: {len(inserted_ids)}") 
    print(f"生成的全部 ID 分别是: {inserted_ids}")

方案二：如果只是为了确认是否成功，直接相信代码流程

如果你传入了 10 条数据，且语句没有因为唯一键冲突（Unique Violation）或外键约束而抛出 SqlAlchemyError 异常，那么在 with 上下文结束后，这 10 条数据就必然已经 100% 成功插入了。

try:
    with get_db() as session:
        session.execute(insert(User).values(data_list))
    print(f"没有抛出异常，成功插入了 {len(data_list)} 条数据！")
except Exception as e:
    print(f"插入失败，原因: {e}")

方案三：如果你非要死守 rowcount（必须关闭高速批量优化）

如果你在写一些通用的旧逻辑，必须通过 rowcount 拿到数字，你需要强制告诉 SQLAlchemy 不要合并这次批量执行（这会牺牲一部分批量插入的性能）：

with get_db() as session:
    # 强制在执行选项中关闭批量执行优化机制
    result = session.execute(
        insert(User).values(data_list),
        execution_options={"preserve_rowcount": True} # 或关闭批量合并
    )
    # 此时在某些 psycopg 版本中可以拿到 rowcount，但不保证所有版本兼容
    print(result.rowcount)

ResourceWarning: <psycopg.Connection object at 0x11dd56120> was deleted while still open. Please use 'with' or '.close()' to close the connection properly

出现 ResourceWarning: <psycopg.Connection object at ...> was deleted while still open 的原因是：程序结束时，底层的 psycopg 数据库连接仍在连接池中保持打开状态。SQLAlchemy 会在连接池中缓存连接以供复用，但当整个脚本退出时，Python 的垃圾回收器在引擎销毁前销毁了这些连接对象，从而触发警告。

以下是出现该警告的常见原因及对应的标准解决方法：

1. 脚本结束前未释放连接池（最常见）

在运行独立的 Python 脚本或自动化测试时，执行完数据库操作后程序直接退出。此时，db_engine 维护的连接池（Connection Pool）里还保留着活跃的 psycopg 连接。

  • 解决方法：在脚本彻底结束前，显式调用 db_engine.dispose() 来关闭连接池中的所有物理连接。
try:
    with get_db() as session:
        session.execute(stmt)
finally:
    # 程序退出前，强制关闭引擎连接池里的所有连接
    db_engine.dispose()

2. 直接使用 engine.connect() 但没有关闭

如果你在代码中使用了底层连接（例如前面提到的 inspect(engine.connect())），并且没有使用 with 块或调用 .close()，连接就会直接泄露。

  • 错误写法：
conn = db_engine.connect()
inspect(conn).get_table_names() # 忘记关闭 conn
  • 正确写法：
with db_engine.connect() as conn:
    tables = inspect(conn).get_table_names()
# 离开 with 块时，连接会自动归还并正确管理

3. session.close() 未正确执行

如果你在最初的公用函数封装中，没有把 session.close() 放在 finally 块中，一旦中间发生异常，数据库连接就会一直处于游离的打开状态。

  • 检查你的公用函数：确保 finally 块完整存在。
@contextmanager
def get_db():
    session = db_session()
    try:
        yield session
        session.commit()
    except Exception:
        session.rollback()
        raise
    finally:
        session.close() # 确保这行代码无论如何都会执行

4. 如果不需要连接池（适合短生命周期脚本）

如果你的代码只是一个每次运行几秒钟就退出的定时任务或测试脚本，根本不需要维护连接池，可以在创建 engine 时直接禁用连接池（使用 NullPool）。

  • 作用：每次 session.close() 时，底层 psycopg.Connection 会被立即物理关闭，不会留在内存中等待回收。
from sqlalchemy import create_engine
from sqlalchemy.pool import NullPool

# 禁用连接池，用完即刻物理关闭连接
db_engine = create_engine(url=db_url, future=True, poolclass=NullPool)

sessionmaker 创建的 session 如何 close

在 SQLAlchemy 中，关闭由 sessionmaker 创建的 session 非常简单，根据你的调用方式，主要有以下三种标准做法：

1. 手动调用 .close()（最直接）

如果你是直接实例化 session = db_session()，在操作完成后，直接调用实例的 .close() 方法即可。为了防止代码中途报错导致跳过关闭步骤，通常需要配合 try...finally 使用。

session = db_session()
try:
    # 执行数据库操作
    session.execute(stmt)
    session.commit()
finally:
    # 明确关闭 session，将连接释放回连接池
    session.close()

2. 使用 with 语句自动关闭（最推荐）

如果你不想手动写 .close()，sessionmaker 生成的实例本身支持上下文管理器协议。只要代码离开 with 缩进块，无论是否发生异常，session.close() 都会被自动调用。

with db_session() as session:
    session.execute(stmt)
    session.commit()
# 离开此处时，底层自动执行了 session.close()

3. 批量关闭所有活跃的 Session（特殊场景）

如果你在全局创建了多个 session 实例，想在程序清理阶段一次性全部关闭，可以使用 SQLAlchemy 提供的全局清理函数 close_all_sessions()。

from sqlalchemy.orm import close_all_sessions

# 一键关闭当前内存中所有由 sessionmaker 创建的 session
close_all_sessions()

💡 关键补充：为什么调用了 session.close() 还是报连接未关闭的警告？

结合你上一条提到的 ResourceWarning 报错，需要理解一个核心机制：session.close() 只是把连接“归还”给 SQLAlchemy 的连接池，并没有真正断开与 PostgreSQL 的物理 TCP 连接。

如果你在脚本彻底退出前，没有清理连接池，依然会看到警告。因此完整的彻底关闭流程应该是：

  1. session.close()：结束当前会话，归还连接。
  2. db_engine.dispose()：在程序完全退出前调用，销毁连接池，彻底断开所有底层的 psycopg.Connection。

get_bind().dispose() 和 dispose() 的区别

在 SQLAlchemy 中，这两个方法最终调用的底层逻辑是完全一样的，唯一的区别在于调用的主体对象不同（一个从 Session 出发，一个从 Engine 出发），以及在某些复杂绑定场景下的行为差异。

以下是两者的具体对比与使用场景：

1. db_engine.dispose()（直接调用）

  • 调用主体：Engine 对象本身。
  • 作用：直接销毁该 Engine 维护的整个连接池（Connection Pool），关闭所有空闲的物理数据库连接。
  • 适用场景：你在当前作用域中直接持有了 db_engine 变量。这是最直接、最推荐的写法。
# 直接通过引擎对象销毁连接池
db_engine.dispose()

2. session.get_bind().dispose()（间接调用）

  • 调用主体：Session 对象。
  • 执行过程：session.get_bind() 会先顺藤摸瓜找到当前 session 绑定的底层 Engine（或 Connection），然后再调用它的 .dispose() 方法。
  • 适用场景：在你的当前函数或模块中，只拿到了传入的 session 对象，而没有直接引入全局的 db_engine 变量。
def cleanup_in_module(session: Session):
    # 手头没有 db_engine，通过 session 反向获取绑定的引擎并销毁
    engine = session.get_bind()
    engine.dispose()

⚠️ 使用 session.get_bind().dispose() 的潜在风险

虽然它们通常指向同一个底层引擎，但在使用 session.get_bind().dispose() 时需要注意两个重要细节：

  • 影响范围是全局的：即使你是通过某一个局部 session 调用的，它销毁的是整个全局 Engine 的连接池。这会导致其他正在共享这个 Engine 的 session 失去连接池。
  • 类型安全与返回值不确定：在多数据库路由（读写分离、分库分表）或 Session 绑定了单个 Connection 而非 Engine 的特殊情况下，session.get_bind() 返回的可能是 Connection 对象而不是 Engine。Connection 对象是没有 .dispose() 方法的，此时调用会直接抛出 AttributeError: 'Connection' object has no attribute 'dispose' 异常。

📊 总结对比

维度 db_engine.dispose() session.get_bind().dispose()
调用起点 Engine 实例 Session 实例
代码清晰度 高（明确表达销毁全局连接池的意图） 中（容易让人误以为只销毁当前会话的资源）
安全性 高（100% 确定调用的是引擎的方法） 中（若绑定的是 Connection 会报错）
推荐程度 强烈推荐（在程序退出清理阶段使用） 仅在无法访问 engine 变量时作为备选

将查询出的数据保存为 xlsx 格式的文件

将 SQLAlchemy 查询出的数据保存为 .xlsx 格式的 Excel 文件，最简洁、高效的方法是使用 pandas 配合 openpyxl 引擎。

以下是两种最常用的场景实现方案（建议先确保安装依赖：pip install pandas openpyxl）：

方案一：将 Result 转为字典列表后导出（最通用，推荐）

利用前面提到的 result.mappings().all() 获取字典列表，直接传给 pandas.DataFrame 即可自动生成带表头的 Excel 文件。适用于 ORM 查询和原生 SQL 查询。

import pandas as pd
from sqlalchemy import select

with get_db() as session:
    # 1. 执行查询
    stmt = select(User.id, User.name, User.email)
    result = session.execute(stmt)
    
    # 2. 转换为字典列表（键名会自动成为 Excel 的第一行表头）
    data = result.mappings().all()

# 3. 转换为 DataFrame 并导出为 xlsx
if data:
    df = pd.DataFrame(data)
    # index=False 表示不把 pandas 默认的 0, 1, 2... 行号写入第一列
    df.to_excel("users_export.xlsx", index=False, engine="openpyxl")
    print("导出成功！")
else:
    print("查询结果为空，未生成文件。")

方案二：使用 pd.read_sql() 一步到位（最简短，适合原生 SQL 或 Core 语句）

如果你不需要在 Python 代码中对每行数据做复杂的业务逻辑加工，可以直接把 SQL 语句和数据库连接交给 pandas 内部处理，代码量最少。

import pandas as pd
from sqlalchemy import select

stmt = select(User)

# 直接通过 engine 建立连接并读取为 DataFrame
with db_engine.connect() as conn:
    df = pd.read_sql(stmt, con=conn)

# 导出为 Excel
df.to_excel("users_direct.xlsx", index=False, engine="openpyxl")

💡 常见避坑指南（PostgreSQL 专属）

带时区的时间字段报错：PostgreSQL 的 TIMESTAMPTZ（带时区时间）在导出到 Excel 时，经常会触发 ValueError: Excel does not support datetimes with timezones 错误。

  • 解决方法：在导出前用 pandas 去除时区信息即可：
# 假设 created_at 是带时区的时间列
if "created_at" in df.columns:
    df["created_at"] = df["created_at"].dt.tz_localize(None)

不想引入庞大的 pandas 库：如果你的项目环境对安装包体积敏感，只想用轻量级的纯 openpyxl 导出，也可以直接遍历 result.all() 逐行写入工作表（ws.append(list(row))）。
